# Сценарій демо спринта 2

Продукт «ШопЛайн» · команда С · спринт 2 «Аудит вимог і стратегія тестування» · жовтень 2026

Автор і доповідач: Гаєвський А. (керівник тестування). На питання відповідають усі; хто відповідає за що — у таблиці наприкінці.

## Хронометраж (10 хв)

**0:00–1:00 — контекст.** Замовник передав SRS «ШопЛайн» 1.0: 42 вимоги у шести розділах (14 F, 11 GUI, 8 BL, 9 нефункціональних разом із рядком без ID). Завдання — перевірити якість специфікації до тестування і запропонувати стратегію. Кожен розділ незалежно перевіряли двоє, потім зведення, обговорення спірних, SRS 1.1 і план.

**1:00–4:00 — реєстр дефектів** (показати аркуш «Зведення» у requirements-defects.xlsx).
Прийнято 25 дефектів, норматив для 4 осіб — 16. По критеріях: однозначність 4, повнота 4, несуперечливість 5, простежуваність 4, здійсненність 4, тестопридатність 4. Ще 3 знахідки відхилено після обговорення, вони лишаються в реєстрі зі статусом. Найбільше дефектів у розділі 3 (F) і на перетині розділів 3, 4, 5 — несуперечливість шукали, порівнюючи F, GUI і BL між собою.

Три показові дефекти:
1. *Очевидний* — № 24, S-10 «система не містить вразливостей». Відсутність усіх вразливостей довести неможливо, тест не має результату «пройдено». Виправлення: HTTPS, хеш паролів, 401/403 для API, ZAP baseline без High.
2. *Спірний* — № 21, P-10 «0,1 с за будь-якого з'єднання». Сперечались між здійсненністю і тестопридатністю. Обрали здійсненність: виправлення робить значення досяжним (3 с при 10 Мбіт/с), а умови вимірювання — наслідок.
3. *Найважливіший для наступних спринтів* — № 9, поріг безкоштовної доставки: F-110 «від 2000 грн» проти BL-60 «від 1500 грн після знижки». Від нього залежать тест-кейси оформлення замовлення (спринт 3) і юніт-тести shippingFee (спринт 4) — без рішення один із двох наборів тестів буде хибним.

**4:00–6:00 — SRS 1.1** (показати журнал змін у SRS-1.1.md).
26 рядків журналу, кожен з № дефекту. ID не перенумеровано: форма реєстрації отримала GUI-65, рядок без ID — U-30, BL-30 вилучено з «діркою». Шість правок мають позначку «потребує підтвердження замовником» — це питання наприкінці.

**6:00–9:00 — план тестування** (показати test-plan.md).
7 рівнів, 17 застосовних типів (норматив 12), 7 незастосовних з обґрунтуванням природою продукту. High: модульне, інтеграційне, smoke, системне, приймальне замовником; типи — функціональне, захищеності, потоків даних, умов гонок. Два приклади Ціль / Опис:
- *Захищеність:* покупець A не бачить інвойс покупця B — підставляємо ID в /invoices/{id} і в API, очікуємо 403.
- *Умови гонок:* одноразовий промокод не застосовується двічі паралельними запитами — два потоки викликають apply, друге застосування повертає ALREADY_USED.
Незастосовні: інсталяційне (вебсервіс), доступності й відновлення (немає вимог, один екземпляр, дані demo скидаються штатно). Навантажувальні тести — лише на локальній Docker-копії, бо навантажувати публічний demo неетично.

**9:00–10:00 — питання замовнику** (customer-questions.md, пункти 1–3 озвучити, решту показати списком).
